# 京东快车轮换助手

京准通快车推广计划的自动轮换工具。计划出单后自动让旧计划退场并建一条新的，用后台静默浏览器运行，不占用你日常使用的浏览器。

本机运行、本机存储：不上传任何数据，不导出 Cookie、Token 或账号密码。

## 它做什么

按设定的间隔检查每个 SKU 的当前推广计划：

- 没有计划 → 建一条新的并启用
- 计划被平台暂停 → 自动重新启用
- 观察期未到 → 继续观察
- 出单达到阈值 → 让旧计划退场，建下一轮新计划
- 今日花费或轮换次数触顶 → 停手

## 安装

需要 macOS 或 Windows，以及**官方稳定版 Google Chrome**。

```bash
uv venv --python 3.11 .venv
uv pip install -e ".[dev]"
.venv/bin/python -m jdka.cli ui
```

浏览器会自动打开控制面板。

## 使用

1. 点「登录京准通」，在弹出的普通 Chrome 窗口里登录一次，然后点「我已登录」。
2. 添加 SKU，填日预算和目标成交成本。
3. 先点「预览检查（只读）」确认判断符合预期 —— 这一步不会做任何写操作。
4. 确认无误后点「开始自动轮换」。

命令行：

```bash
jdka doctor     # 环境自检
jdka preview    # 跑一轮只读预览
jdka ui         # 控制面板
```

## 轮换在什么时候进行

轮换由应用内的后台线程按固定间隔轮询驱动，**默认 20 秒**一轮，可在界面里改
（10–3600 秒）。每一轮做的事就是「运行控制」里那条决策链。

**只在应用运行期间进行。** 退出应用、关机或电脑休眠，轮换都会停止；
后端进程随应用一起结束，不会在后台偷偷跑。

**点窗口的关闭按钮只是收起窗口，应用会继续在托盘（菜单栏）里运行，轮换不中断。**
要真正停止，从托盘菜单选「退出」，或用 Cmd+Q。托盘菜单还可以把窗口唤回来。

默认需要每次手动点「开始自动轮换」。勾选**「打开应用后自动继续轮换」**之后，
下次打开应用会自动接着跑，不必再点。该开关默认关闭 —— 自动轮换会真实花钱，
不该在用户只是「打开看一眼」时就悄悄开始。

想要真正 7×24 无人值守（关掉窗口也继续、开机自启、崩溃自动拉起），
需要额外做成系统服务，当前版本不含这部分。

## 安全设计

这个工具会代你操作真实的广告计划和真实的钱，因此默认取保守值。

**旧计划默认只暂停，不删除。** 删除不可撤销。上游项目出现过「接口回执全绿、写后复核也通过，但平台上的实际状态是错的」的真实故障，所以不把不可逆动作设为默认。要开永久删除，得在设置里显式选择并二次确认。

其余护栏：

- 只操作名称以 `AUTO_` 开头、且与记录完全一致的计划；绝不碰人工建的计划。
- 每日花费上限与轮换次数上限在本地强制执行，不只依赖平台预算。
- 写请求永不自动重试 —— 结果不确定时宁可停下来，也不重复下单。
- 旧计划退场前先落盘完整指标快照，便于人工复核或重建。
- 登录态失效时暂停轮换并提示，不反复弹窗骚扰。
- 预览模式全程只读。

## 浏览器

应用使用**独立的浏览器 Profile**，与你日常的 Chrome 完全隔离：

- 绝不读取、连接或关闭你日常使用的 Chrome Profile。
- 后台任务默认无头运行，不会弹窗，也不会堆积标签页。
- 调试端口随机分配，不占用 9222 等常见端口。
- 只在你点「登录京准通」时才打开一个可见窗口，且该窗口不带任何自动化参数。
- 按 pageKey 复用固定页面，并按任务数与存活时长有界回收。

数据目录：

- macOS：`~/Library/Application Support/SankaiAI/JD Kuaiche Assistant`
- Windows：`%LOCALAPPDATA%\SankaiAI\JD Kuaiche Assistant`

登录资料只保存在该目录下的独立 Profile 中，卸载前请自行清理。

## 关于计划状态取值

京准通的计划状态**与字面直觉相反**：`operateType` / `status` 中 **`2` 是启用，`1` 是暂停**。

这一点曾导致上游项目「新建计划总是暂停中」：创建后发 `operateType=1`（实为暂停），而写后复核又断言 `status==1`，两处同错互相印证，日志一路 `enabled:true / verified:true`，只有打开真实页面才能发现。

取值集中定义在 `jdka/jd/shared.py` 的 `PLAN_STATUS_ENABLED` / `PLAN_OPERATE_ENABLE`，并有专门的回归测试钉住语义。**请勿凭直觉改回去。**

## 开发

```bash
.venv/bin/python -m pytest -q
```

发布走 GitHub Releases：推送 `vX.Y.Z` 标签后由 Actions 构建并发布，应用内会提示新版本。

## 边界

- 只支持京准通**快车**的商品-常规推广-关键词定向计划。
- 创建请求由推荐接口的返回值程序化组装，不驱动网页控件。
- 平台接口若发生变更，需要发新版本修复。

## 桌面应用

外壳用 Tauri，业务逻辑仍是同一份 Python 后端：外壳启动时把后端拉起在随机端口，
读取它 stdout 的一行 `JDKA_ENDPOINT {...}` 拿到端口与访问令牌，再交给界面。
界面是同一个 `jdka/ui/index.html`，浏览器模式与桌面模式共用一份源文件。

```bash
npm install
npm run backend:build     # 用 PyInstaller 打出后端可执行文件
npm run tauri dev         # 开发（开发期直接调用仓库 venv，不必每次重打后端）
npm run tauri build       # 生成 DMG / NSIS 安装包
```

退出应用时会一并结束后端及其拉起的后台浏览器，不留孤儿进程。

### 自动更新

应用启动后查询 GitHub Releases，有新版会在界面顶部提示。下载走 Rust 侧实现，
并强制两条约束：下载地址必须落在本仓库 `releases/download/` 路径内；下载完成
后校验 SHA-256，不通过立即删除。

不做静默自替换 —— 在 macOS 上改写正在运行的 `.app` 会破坏代码签名与公证，
因此校验通过后交由系统打开安装包，由用户确认。

### 发布

推送 `vX.Y.Z` 标签后，Actions 会先用 `scripts/sync_version.py` 把版本同步到
`jdka/version.py`、`pyproject.toml`、`package.json`、`tauri.conf.json` 和
`Cargo.toml`，再在 macOS 与 Windows runner 上分别构建，两端都成功才发布 Release。

### 尚未完成

安装包目前**未做代码签名与公证**：macOS 上 Gatekeeper 会拦截（需右键打开），
Windows 上 SmartScreen 会告警。正式对外分发前需要 Apple Developer 账号与
Windows OV 证书。

## 授权码

本软件需要授权码才能使用，**授权码永久有效，且只在签发时指定的那台设备上可用**。

买家流程：安装打开 → 激活页显示**设备码** → 把设备码发给作者 → 粘贴换来的授权码 → 永久激活。

作者签发：

```bash
python scripts/issue_license.py <设备码> --note 客户名
```

签发会自动记入台账 `~/Desktop/jd-kuaiche-授权记录.jsonl`（客户丢了授权码可直接查回重发，
不必重新签发；也能回答「一共卖给了谁」）。加 `--no-record` 可跳过。

私钥默认读 `~/Desktop/jd-kuaiche-签发私钥-请妥善保管.pem`。
**私钥绝不能进仓库、也不要发给任何人** —— 泄露等于任何人都能自行签发。
仓库里只有公钥（`jdka/license.py` 的 `PUBLIC_KEY_B64URL`）。

### 技术细节

- 授权码是 Ed25519 签名的 `JDKA1.<payload>.<签名>`，离线验证，不需要联网也不需要服务器。
- 设备码 = `SHA-256(installation_id + device_secret + 命名空间)`，两个随机值只存本机、从不上传。
  **不使用**硬件序列号 / MAC / 硬盘序列号 —— 既涉及隐私，也会因换网卡、虚拟机而漂移。
- 校验放在**后端**：未激活时所有业务接口返回 402，藏掉界面不构成保护。
- 签名对象是 payload 的 base64url **字符串本身**，验签通过后才 decode 读字段。

### 这套机制能防什么、防不了什么

**能防**：别人无法伪造授权码（没有私钥）；一份授权码拷到另一台设备立即失效；
改 payload 而不重签会被签名校验拒绝。

**防不了**：拿到二进制并且愿意改代码的人，有可能把校验逻辑整段绕过。
任何纯本地校验都绕不开这一点，除非把核心功能放到服务端执行。
对「防止随手转发授权码」是有效的，对「防专业逆向」不是。

### 换设备 / 重装

设备码存在数据目录的 `identity.json`。清空数据目录会生成新设备码，需要重新签发。
换机器同理 —— 把新设备码发来重签一份即可。

### 发布源必须公开

买家的客户端不带任何凭据，而 GitHub API 对**私有仓库的匿名请求一律返回 404**。
因此发布源必须是公开仓库，否则更新检查在买家机器上永远拿不到数据，
而且症状具有迷惑性 —— 看起来像「尚未发布任何版本」。

本仓库已公开，更新链路可用（匿名请求 `releases/latest` 返回 200）。

如果日后想把源码转回私有，更新功能不会自动失效，但需要改为
**源码私有 + 单独一个只放安装包的公开仓库**：

1. 建一个公开仓库，例如 `jd-kuaiche-assistant-releases`（不放源码，只放产物）。
2. 把 `jdka/update.py` 的 `RELEASE_REPO` 与 `src-tauri/src/updater.rs` 的 `REPO`
   同时改成该仓库（两处必须一致，已有测试钉住）。
3. 让 `desktop-builds.yml` 的发布步骤带 `--repo <发布仓库>`，并配一个有该仓库
   写权限的 PAT。

**不要**把 GitHub Token 打进客户端换取私有仓库访问 —— token 会随二进制一起分发，
等于公开，且撤销后所有已安装的客户端同时失效。

### 源码公开对授权码锁的影响

源码公开后，任何人都能读到 `jdka/license.py`、删掉校验并自行编译。
授权码锁此时只能拦住「随手转发授权码」，拦不住有能力重新编译的人。

若要把保护做实，唯一有效的方向是把核心逻辑放到服务端执行 ——
客户端再怎么加固，代码在对方机器上跑就一定可以被改。

## 与上游 ecommerce-store-ops 同步

本项目是从 `ecommerce-store-ops` **复制**出来的（上游一行不改），因此两边会分叉：
上游修了 bug，这边不会自动拿到。

`scripts/sync_upstream.py` 把「抽取时做过哪些适配」显式声明成规则，于是可以做
**归一化对比**——先把上游文件套上同样的适配再比，剩下的差异就是真正的漂移。

```bash
python scripts/sync_upstream.py          # 对账，列出哪些文件与上游不一致
python scripts/sync_upstream.py --diff   # 连同具体差异一起看
python scripts/sync_upstream.py --pull   # 把上游改动同步过来（覆盖本地）
python -m pytest -q                      # --pull 之后必须跑
```

对账范围只有**抽取自上游的 6 个文件**（`jdka/jd/*.py` 三个 + `jdka/core/*.py` 三个）。
本项目自有的部分（`browser/`、`engine.py`、`license.py`、`server.py`、`service.py`、
桌面外壳）上游没有，不参与对账。

### 什么时候跑

- 上游改了京准通接口契约、状态语义、轮换策略之后；
- 发新版本之前，顺手对一次账。

### 适配规则失效时

如果上游把某段被适配的代码整体改写了，脚本会提示「适配规则已失效」。
这不是误报——说明那处上游变了，需要人工确认后更新 `ADAPTATIONS` 里的规则，
否则该文件会一直报差异。
